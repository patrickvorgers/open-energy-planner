# AI development agreements

These instructions apply to the entire repository. Read the requirements, release scope and relevant technical design before changing behaviour. Keep implementation progress distinct from product-release readiness.

## Language and architecture

- This repository is public. Never commit or attach private or personal data, passwords, access tokens, private keys, real Home Assistant configurations, personal measurements, production database files or sensitive logs and screenshots. This also applies to branches, pull requests, issues and CI artifacts. Use independently generated synthetic examples and test fixtures. Review new files and changes for sensitive content before every push. Follow [the security policy](SECURITY.md). Removing an exposed file from the latest commit does not remove it from Git history. Stop publication of suspected sensitive content and notify the owner. Revoke or rotate exposed credentials.
- Before every public push, verify that both author and committer metadata of every introduced commit use the user's confirmed GitHub noreply address. Configure the identity for this repository rather than silently changing global account settings. Keep every commit signed and verify GitHub reports it as Verified after pushing. Never publish private contact addresses in commit metadata. Replacing a branch head does not prove that GitHub removed an earlier exposed commit.

- Use English for documentation, file and directory names, code, comments, tests and UI text.
- Use complete sentences instead of em dashes or semicolons in prose. This includes documentation, comments, docstrings, UI text and logs. Keep punctuation required by programming languages, queries, protocols and literal technical examples. Preserve vendored code and licence text verbatim.
- Short headings, field labels and structured data summaries may remain phrases. The punctuation rule does not require expanding concise labels into verbose narrative.
- Use descriptive Python variable and parameter names, including loops, comprehensions, lambdas, helpers and tests. Prefer domain roles such as `battery_flow`, `interval_index`, `duration_hours`, `ports` and `add_constraint` over single letters or cryptic abbreviations. Use `_` only for an intentionally unused binding. Preserve external protocol/database fields and third-party attributes. SQLAlchemy's `Table.c` is not an application variable. See the naming guidance in the code documentation standard.
- Keep calculation logic in the app and the HA integration thin. Physical device control and safety remain in user-owned HA automations and local equipment.
- Keep HA/provider dictionaries, HTTP clients, ORM sessions and native solver objects inside their adapters. Use small typed contracts, focused classes and composition across module boundaries.
- Preserve original plans, independent scenario expectations and measurement/source evidence. Do not regenerate expected results merely to make a changed solver pass.

## Change validation

- Prefer tests that execute behavior and assert independently specified outcomes. Do not prove functionality by searching for source-code literals, identifiers or generated HTML fragments. Use browser interaction for UI behavior and decode persisted documents before checking their meaning or replaying them. Literal wire values and contractually important user text may be asserted directly. Retain explicit structural checks for import boundaries, packaging, security policies, translation parity and documentation coverage. Never import a production constant or enum as the sole oracle for its own external representation. Use existing enums or focused domain enums for closed decision states, preserving API and archive values. Do not turn arbitrary labels, identifiers or external JSON keys into enums.
- Develop on a focused branch and submit a pull request. Explain the implemented requirement, resulting behaviour and remaining limitations.
- When changing the frontend, coding agents must include screenshots in the pull request whenever their tools support capturing and attaching them. Capture the actual changed interface and relevant states at desktop and mobile sizes. Keep credentials and private data out of screenshots. If capturing or attaching screenshots is unavailable, state that limitation in the PR and report the visual checks actually performed. Use isolated browser-extension tabs for PR screenshot work without taking over the user's visible desktop. Do not fall back to native Windows input or expand extension permissions merely to attach screenshots. If the existing extension cannot upload them, retain the synthetic captures in CI artifacts and link that evidence from the PR. Confirm the images load before claiming they are visible in the PR.
- Add meaningful tests for new functionality and corrected defects. For dependency updates, assess whether compatibility or behaviour changes need additional regression coverage.
- Durable configuration, rules, counters, source/model archives and plans belong in the active database. Keep database connection settings, access tokens, certificates and technical logs outside it. No converters for unreleased development files/schemas are required. Only cross-backend transfer is supported.
- All OEP database tables belong to the shared SQLAlchemy schema and app-owned active engine. Backend migration transfers and verifies every table. Runtime/restart must not depend on the source afterward. New stores must join that schema and its migration tests.
- Every database change must update [the database schema and data dictionary](docs/development/DATABASE-SCHEMA.md) in the same PR, including changed tables, columns, types, constraints, relationships, indexes, units, JSON contracts, ownership and usage as applicable. The documentation test enforces table/column coverage. Reviewers must verify meanings and query assumptions, including changes that do not add or remove columns.
- All existing and new database contract/migration tests must use the shared matrix in `tests/database/support/backends.py`: SQLite, PostgreSQL, MariaDB and MySQL. CI must run real instances and fail when a required backend is unconfigured. MariaDB is not proof of MySQL compatibility.
- Run Ruff, formatting and the affected regression tests locally. Include desktop/mobile Playwright checks for affected browser flows and targeted HA, database or Supervisor proof when the changed behavior needs it. Execute the complete required suite set once through the GitHub candidate workflow, not as an automatic duplicate local prerequisite. GitHub-hosted execution is the default. The personal repository owner can apply `ci-runner: prefer-local` before choosing Ready for review to prefer their Linux x64 runner in Docker. Only reviewed private same-repository PRs authored and requested by the personal repository owner can use the generic `oep-ci-local` runner. Other contributors always use GitHub, even when the preference label is present. Unknown owner metadata and organization-owned repositories cannot select local execution. Offline, busy or unverifiable personal capacity falls back to GitHub. Never treat a coding agent's claim of local success as candidate evidence. An additional full local `python script/ci/ci.py` run needs a concrete diagnostic reason or an explicit request for that run. Record its reason and actual result in the PR. The same current-head/base candidate, package and reuse evidence remains mandatory for either runner location.
- During development and review, run `python script/ci/check_native.py --quick` and the affected regression tests locally. Group related review corrections into one tested push. Do not push each comment fix separately or repeatedly start the full suite while the candidate is changing.
- Build and review PRs in Draft. Every revision receives automatic Quick checks and trusted signature verification, including Drafts. Limit every PR to 150 changed files, including binary, removed and renamed files. Wait for current-head Quick checks, verified commits and CodeQL, then use one independent local Codex context to review the Draft. Record its reviewed SHA and finding dispositions. Batch corrections and retest instead of requesting independent review on every push. Only then freeze the final head and base. When choosing CodeRabbit, run the trusted-main Manual CodeRabbit review preflight. Kody-ai is an alternative under the same independent-review, queue and finding-disposition requirements. Its read-only summary provides the manual command and head marker. It neither requests review nor reserves quota, and its attestations do not prove semantic review correctness. Automatic, incremental, label and description-keyword CodeRabbit triggers remain disabled regardless of stars or paid plan. Develop Drafts and run independent local Codex reviews in parallel, but request final CodeRabbit reviews in the intended merge order. Finish the preceding PR merge and its required main checks, include that actual main in the next PR, resolve conflicts and rerun affected checks and CodeQL before freezing its final head and base. Review availability does not justify reviewing a later queued PR early. The preflight verifies that the current base is included in the head, while the coordinator remains responsible for the human merge order. Coordinate one queue across all chats, respect actual provider reset information and never retry autonomously. Do not request CodeRabbit for Dependabot PRs, which retain their documented exception. Verify actual completed scope, workspace, analysis, feedback and publication for the current head. New, reopened, revised or retargeted PRs return to Draft. After latest-head review and evaluation, replies and resolution of every finding, including outside-diff comments, choose Ready for review to request one candidate automatically. Ready is the operator attestation of complete finding disposition. Admission also rejects unresolved review threads. A completed current-head review is always required. Previously reported findings are allowed after evaluation, replies and resolution where applicable. New commits cancel obsolete candidates and require a fresh Ready transition after review. Use `ci: run` only for deliberate retries on a frozen, reviewed non-Draft candidate, through the same gates. A retained label never requests CI for a new commit. Do not add periodic checks or automatically retry failed tests. The candidate gate enforces the 150-file limit, successful current-head Quick checks, verified commits, CodeQL and substantive completed CodeRabbit or Kody-ai review, with the existing Dependabot exception. It does not replace manual evaluation of all review findings.
- Merge only after the requested candidate's `Quality and integration (AMD64)` job actually succeeds on the current PR head and intended base. A missing, pending, cancelled or skipped full result is not a passing merge check. Recheck the review, findings and identities before merge. Do not accept an older revision's test result. Main pushes may reuse an identical successful full or focused product PR candidate only through the checked main-reuse gate. Focused product reuse requires the independently verified first-parent profile, its exact selected-suite tree marker and both original bundle and reports. Strict owned Python test-only candidates may instead reuse exact-profile report evidence after independent first-parent policy verification, without an installation bundle or deployment identity. Missing proof or artifacts retain full checks. Manual and release events always retain full checks. See [review and CI stages](docs/development/CI-STAGES.md).
- Candidate CI selects suites using the change-based matrix in [review and CI stages](docs/development/CI-STAGES.md). Execute the immutable base revision's policy against the entire PR base and intended merge tree. Never select from only the last commit. Union all affected suites and default uncertainty, special modes, unreviewed shared composition and unknown impact to full validation. Installation and lifecycle owners require their explicit provisioning, backend and/or Supervisor contracts. Do not infer a cumulative full profile from independent suite unions. All database changes retain the real four-backend matrix. Every route retains verified commits, completed latest-head CodeRabbit or Kody-ai review and evaluated, replied-to and resolved findings. Manual and release runs remain full. No nightly or periodic full run is scheduled. Main may reuse an identical successful full candidate with its original available bundle. An identical focused product candidate may reuse its original bundle and reports after independent first-parent policy/profile verification. Strict Python test-only candidates retain report-only reuse. Mixed known changes retain the complete suite union. Unknown ownership, differing trees and missing proof retain full main CI. Focused candidate success is not full-suite or deployment evidence.
- Use the default lint rules of the pinned Ruff version plus the explicitly agreed missing/empty-docstring rules D100-D107 and D419, configured centrally in `pyproject.toml`. These rules cover tests and browser tests too. Do not add test-path exemptions. Do not add further custom rule selections or suppressions without an agreed reason. The Dev Container editor and CI use the same installed Ruff version. Both lint and format checks must pass.
- When introducing a quality control, correct existing violations in its agreed scope immediately. Do not grandfather them through a baseline, debt register or legacy suppression. Any exception needs an explicit user decision. Report the exact boundary of what the check can prove.
- Do not claim live hardware, browser behaviour, platform compatibility or CI success unless actually verified. Use isolated development HA and fixtures. Do not access production devices or credentials without authorization.
- Keep numbered deployment provenance intact. Released app and integration artifacts must identify the same tested source. Never copy source overlays onto a numbered installation or invent its build number. Rebuild/restart the loaded components and verify their identities before reporting success. Use the isolated [real Supervisor developer environment](docs/development/DEVELOPER-ENVIRONMENT.md) for development. Persistent `oep-dev` updates require the original numbered CI installation bundle from a successful candidate with all required CI suites whose tested tree equals its GitHub Verified merge on main. Use `script.supervisor.dev update --bundle <zip> --run-id <id>` from that clean merged checkout. Never prepare persistent installations from loose source files. Verify both loaded component build identities after updating. Unmerged source acceptance remains confined to `script.supervisor.check_supervisor` and its disposable project. Personal HA OS machines and their deployment are outside this repository's required test and merge workflow. Preserve existing data and IDs. See [joint release identity](docs/development/RELEASE-IDENTITY.md).
- Sign every commit, including follow-up fixes, rebases and merge commits. Verify GitHub reports the pushed commit as **Verified**. Never disable signing to work around a failure or copy private keys into containers.
- The `GitHub Verified PR commits` Actions job must pass for every introduced commit. It runs only trusted base code via `pull_request_target`, never PR-controlled code, and verifies the complete base/head history through GitHub. Use the Actions job result without publishing a duplicate legacy commit status. Its token needs only read access. Trusted workflow changes activate after merging onto main. A verification outage is a failed check, never a passing result. This is an owner-approved CI quality check, not server-enforced branch protection: same-repository writers are not an adversarial security boundary. Keep the repository private until owner-authorized publication passes an audit of history, references, attachments and Actions evidence. Stop and unregister every personal runner before public visibility. Public contributions use GitHub-hosted runners without personal runner credentials or access to private infrastructure. No paid upgrade is authorized.

## CI ownership

- Group ordinary domain behavior, storage, example provisioning and platform lifecycle by responsibility. Reuse established domain directories; ordinary example-data tooling and assertions belong in `script/provisioning/` with tests in `tests/provisioning/`. Keep Supervisor API/ingress/install/restart/update control and mixed bootstrap outside ordinary domain/provisioning owners.
- New files inherit known-area coverage. Unknown domains, shared infrastructure and unclear ownership require full CI until reviewed. Never move code into a cheaper area merely to bypass a suite. Preserve whole-PR selection, both sides of moves, real four-backend contracts, provisioning/retention checks and full manual/release validation.
- Use the responsibility map in [CI stages](docs/development/CI-STAGES.md). Collect suites by directory. New test files must have a declared area. Keep reviewed calculations in `core/` and domain `calculation/` directories, Supervisor control in its own owner, schema, migration and retained repository startup in `storage/adapters/lifecycle/`, app-side HA contracts in `home_assistant/`, page rendering in `frontend/`, and startup in `runtime/`. The storage and HA routes combine independently. Splitting tests alone does not authorize omitting contract or lifecycle proof.
- Keep CI metadata proof in its explicitly reviewed owners and fixed Git processes in `script/ci/proof_git.py`. New imports and helpers must pass the transitive proof ownership guard. Never add Docker, database, HA or arbitrary process execution to a cheap proof owner or its native CI service. Unknown CI files and shared execution owners retain conservative coverage. Keep presentation in `scope_report.py`, consuming captured decisions without recomputing selection or writing Actions outputs. Keep the selector and every imported helper in a self-contained snapshot of the same immutable base. Run it with isolated Python and site initialization disabled. Preserve legacy standalone-policy compatibility. Pure suite membership belongs in `ci_groups.py`. HA arguments and partition rules belong in the guarded pure HA owners. Admission and reuse workflow metadata belongs in `ci-admission.yaml` under its fixed read-only command/action contract. Shared process launch, image collection and pytest execution retain conservative coverage. Never grow these pure or metadata owners with workload execution. HA harness changes must run the real HA workers, contracts and provisioning through the independently selectable `ha` parent. See [metadata proof ownership](docs/development/CI-STAGES.md#metadata-proof-ownership).
- Selection summaries must show required and omitted suites with reasons. A selected suite counts only after successful execution; incomplete completion evidence must block packaging, full-tree publication and candidate reuse. Static ownership tests complement review, not a complete dynamic dependency proof.

Keep independent query, ordinary restart, index repair and active-archive integrity assertions under `tests/database/contracts/`. Do not classify slow functional checks as performance.
- `databases` retains both functional groups for legacy profiles and immutable base policies. `database-contracts` and `database-migrations` are independently selectable children with their own collection, JUnit and completion proof. `full` must never lose functional transfer coverage. All selected groups use the shared real four-backend matrix.
- Writers, schema, archive formats, serializers, backend adapters and shared fixture changes retain migration coverage. A query may omit transfers only inside the guarded read-only SQL query ownership. Keep schema initialization, row mutation, transactions and serialization outside that owner. `from sqlalchemy import select` is the sole reviewed SQLAlchemy import in this owner, including its transitive helpers. Execute only direct Select expressions. Raw driver access, borrowed SQL statements and saved execute aliases are outside this reviewed boundary. Query performance remains an independent decision.
- Put shared scenario inputs in responsible support modules. Do not import a whole scenario module merely for reusable data when that couples an unrelated testcase change to heavy consumers. Preserve all consumers when the actual shared helper changes.

## Central app ownership and selective validation

- Keep flat app modules limited to their documented shared responsibilities. `app.py` owns authentication, mutation ordering and composition. `live_inputs.py` owns input admission and refresh coordination. `planning_policy.py` owns genuinely shared horizon and resolution policy. Put domain calculations, conversions, projections and explanations in their existing domain owner. Put forecast freshness in `installation/forecast_policy.py`.
- A PR extending a flat app module must explain why the behavior belongs centrally, why an existing domain cannot own it and which additional test groups it requires. Do not introduce a registry, plugin layer or generic callback framework merely to avoid editing composition.
- Ordinary domains must not import app composition, live-input coordination, the HA framework or the custom component, directly or transitively. The architecture guard enforces those boundaries. The app-side peer contracts are independently tested without starting Home Assistant. Real device execution, Recorder and platform lifecycle retain their responsible integration groups.
- Known root composition changes retain app, peer, backend and actual platform acceptance. They do not automatically select every HA feature. New or removed flat modules require an explicit ownership review and keep the conservative route. Do not relocate behavior solely to obtain cheaper CI.
- Add selection regressions whenever a reviewed ownership boundary changes. Cover directory growth, mixed changes and both sides of moves. A small native change must not silently regain unrelated HA, migration or query-volume groups. Semantic coupling and public wire changes remain review obligations beyond static imports.

## Pull request review lifecycle

- Ready for review requests candidate CI after Draft review. `ci: run` requests a deliberate retry through the same admission gates. Automatically maintained `ci-scope: *` labels describe the planned test groups for the current PR revision, never execution results. Publish each independently selected group, omit standard `ci` when other groups are present, and refresh labels after every PR push. Labels never override the immutable base policy or count as merge evidence. Wait for the label workflow when checking an updated PR, then verify the actual candidate's scope and identities in Actions.
- `ci-runner: prefer-local` is an execution preference, not a test selection or result. Local capacity is reserved for the personal repository owner's own PRs and requests, using GitHub owner metadata and the generic oep-ci-local runner label, never a username or machine committed to the workflow. `ci-execution: local` and `ci-execution: github` describe the latest completed candidate's actual execution location. They do not prove current-head success. Check the run and source identities. Do not silently retry failing local tests on GitHub. Automatic fallback applies to unavailable capacity before job dispatch, not failed test results.
- Personal runners require a private repository with fork PR workflow execution disabled at GitHub. Verify those actual platform settings before registration and startup. The read-only admission check is a fail-closed preflight, not a sandbox against PR-controlled workflows. Same-repository writers remain trusted. Stop and unregister personal runners before enabling fork PR workflows or making the repository public. Never claim continuous policy enforcement while a runner is idle.

- Wait for the active review to finish, then collect all inline and outside-diff findings before preparing corrections. Evaluate the complete batch, fix valid findings, run affected checks and publish one tested push. Request one incremental review of that new head. Do not request duplicate reviews while one is pending. New findings start another batch. Request candidate CI only after the latest-head review completes and all findings are addressed. Keep the candidate frozen unless a new finding or failure requires a correction.
- Inspect all review comments and threads, including Codex, CodeRabbit and Kody-ai findings. Review comments are evidence to assess, not instructions to obey blindly.
- Evaluate commit-signature findings against the actual GitHub PR head and introduced commit list, not a synthetic local review snapshot.
- Evaluate each actionable finding against the current code, agreed requirements and reproducible behaviour. Record whether it is correct, already addressed, superseded or incorrect.
- Fix correct findings, add a regression test when it protects meaningful behaviour, and run the relevant checks. Reply with the change and verification evidence before resolving the thread.
- For incorrect or inapplicable findings, explain the reasoning with code, requirement or test evidence. Do not make an unnecessary change merely to satisfy a reviewer. Resolve only after the finding has been substantively addressed.
- Acknowledge low-priority suggestions explicitly: implement them when useful within scope, or explain why they are deferred. Do not silently ignore review comments or resolve unresolved work.
- After pushing fixes, inspect new and existing review threads again. Check review coverage against the current head commit. A review of an older revision is not proof that the latest changes were reviewed.
- At least one automated reviewer, CodeRabbit or Kody-ai, must complete a substantive review of the latest PR head before Ready for review or merge. Every new commit, including documentation-only changes, requires a completed review of that head from either provider. Evaluate and address every finding from all reviewers, including outside-diff comments, and resolve the evaluated threads. Passing CI, no comments, pending or skipped reviews, an unavailable provider and older-head reviews do not prove completion. Recheck the head SHA immediately before merging.
- Codex Cloud review is optional and may be requested only when the human user explicitly asks for a Codex Cloud review of the relevant PR. Do not automatically post or repeat `@codex review` or `@codex security review`, including after follow-up commits. A general request to inspect or review a PR does not authorize starting a Codex Cloud review. Inspect the code, checks and existing findings directly. Keep automatic Codex reviews disabled for this repository. Optional Codex review is not an additional automatic merge prerequisite. Existing findings from any reviewer must still be evaluated and addressed.
- Temporary exception for PRs authored by `dependabot[bot]`: Automated review is not a merge prerequisite. CodeRabbit review remains disabled. Do not post manual CodeRabbit review commands. Codex Cloud review also requires an explicit user request. It is not a default requirement for dependency PRs. Passing CI, verified commits, dependency compatibility assessment and regression-coverage assessment remain required. Evaluate any existing findings. This exception does not dismiss them.
- Before reporting a PR as ready, verify required checks and the disposition of actionable findings. Report pending reviews or unavailable review services explicitly. No comments from a service does not prove a completed review.
- Review handling authorizes replies explaining findings and fixes on the relevant PR. It does not authorize unrelated messages, a paid review subscription, broader repository access or merging without applicable user authorization.

## Parallel PR merge coordination

- Coordinate automatically whenever other active OEP work can change `main` or invalidate a candidate. The repository owner authorizes messages between active OEP chats solely to coordinate their shared branch, CI candidates and merge order. Share only the relevant PR, scope, head/base identities, checks, conflicts, run status and merge slot. This standing authorization does not extend to unrelated conversations, other repositories, deployments or merging another PR without its own user authorization.
- Before requesting candidate CI or merging, inspect current GitHub PRs and running candidates, identify the active owners, name one active OEP chat as queue coordinator and agree on the next writer to `main`. Report readiness and any existing candidate before claiming a slot. Only an explicit agreement reserves a slot. Verify reported checks independently in GitHub rather than treating a peer's status claim as passing evidence.
- Preserve the agreed base of an active candidate until its owner merges or explicitly releases the slot. Continue independent local tests and reviews while waiting. Never cancel another owner's run or change their branch to obtain a slot. Prefer ready focused candidates before full candidates when this prevents obsolete expensive runs. Use actual readiness rather than PR numbers, and reassess the order when a predecessor needs more work.
- The idle slot timeout is 15 minutes without an owner progress update and without a queued or running candidate for that reservation. After independently checking GitHub and notifying the affected owners, the repository owner or named queue coordinator may release and reassign an expired reservation without changing its owner's branch or cancelling their runs. If the coordinator is unavailable, the remaining active owners explicitly agree on a replacement first. An expired owner must reacquire a slot and confirm the current base before requesting CI or merging.
- After predecessors merge, fetch `main` and confirm the final intended base before requesting CI. When synchronization is needed, combine the signed sync and related review corrections into one tested push where possible. Require the existing current-head review, signature and selected-suite gates. Documentation-only PRs retain their documentation route. A mixed PR retains every suite required by its actual diff. Coordination never weakens selection or reuses proof for a different tested tree.
- Immediately before merging, recheck the agreed base, PR head, completed review, addressed findings and successful candidate. Use GitHub's PR merge endpoint with `sha` set to the tested PR head. The connected GitHub merge tool names this head guard `expected_head_sha`. It guards the PR head, not the base revision. If the base or candidate changed, refresh the required proof before merging. These instructions are a coordination procedure, not an atomic GitHub merge lock.
- If the actual merged tree differs from the tested tree, treat the merge as unverified, stop further coordinated merges and notify the user and affected owners. Inspect the unexpected changes, restore the required review and authorization gates, and obtain fresh successful CI for the actual tree, using a corrective PR when needed. Do not publish, deploy, release the queue or report success using the stale proof. Never rewrite `main` or remove another owner's work to restore the old tree.
- After merging, independently verify the merge identity, GitHub Verified status and tested-tree match. Notify the waiting OEP owners with the actual merge SHA, base, candidate/run evidence and slot release. Refresh or release the slot explicitly on failure, cancellation or changed scope. Each owner remains responsible for their own PR, verification and authorized deployment scope.

## UI presentation

- Every problem notification must identify the affected configured sensor, device, source or rule when that identity is known, explain the actual failure and affected operation, and give a concrete next step. Put this actionable context in the visible explanation in both the notification center and recovery page. Do not hide it in raw technical details. Never render arbitrary provider errors, payloads, tokens or credentials as an explanation. An unchanged valid HA value is not proof of disconnection. Apply age limits to current integration captures, without treating explicit sample metadata as a sensor heartbeat. Preserve original HA timestamps as provenance and keep command expiry independent.

- Appliance identity/source, physical behavior, forecasting, control capability, permitted planning use and daily intent are separate dimensions. Reuse the existing appliance categories, selected-device editors, shared summary/SaveBar presentation and specialist models under `appliances/`. Retain Add, Edit and removal actions. Keep cycle profiles and their measured evidence under Energy. Do not create a second HA device registry or an all-optional universal solver/form model. Weather-sensitive consumption prediction does not authorize climate control. Household/residual demand remains in `demand/`. See [shared appliance structure](docs/development/APPLIANCE-ARCHITECTURE.md).

- Keep configuration of consumption devices, thermal stores, vehicles and charge points under Settings > Appliances, using shared category navigation and the existing type-specific editor/SaveBar. Energy pages expose monitoring and explicit daily requests only. Reuse existing intent APIs for comfort, readiness, departure and similar actions. Future appliance types follow this ownership boundary without introducing a universal form or solver model. Installation topology remains under Settings > Installation. Preserve drafts when refreshing evidence or refusing category navigation. Keep the displayed device and intent target synchronized before asynchronous refresh.

- An approved prototype is the implementation reference for its complete layout, interactions, spacing, typography, icons and responsive behaviour. Reuse real app data and preserve validation and persistence safeguards. Verify saved, editing, loading and error states against the prototype on desktop, tablet and mobile. Record necessary deviations with their reason and evidence in the PR. Applying only its colours does not satisfy prototype parity.
- Never use a full stop or middle dot as a separator between OEP-owned label, title, caption or structured status/summary fragments. Use a colon followed by a space and start the next text fragment with a capital letter. Preserve ordinary sentence punctuation, abbreviations, decimal points, formulas, URLs, entity IDs and user/provider names verbatim. Apply this at the presentation source, never by rewriting arbitrary rendered text or stored data.
- Visible selection labels use sentence case: start with a capital letter and use readable spaces, while internal enum values remain stable (for example `always` → Always).
- Information popups show each example/selected value on its own line in the same monospace font as formulas, followed by the explanation on the next line. Keep field label, value and explanatory prose separate, including non-formula choices such as annual reset and paid window. Verify the layout on desktop/mobile.
- Show monetary amounts and rates with exactly two decimal places in cards, tables, chart axes/tooltips and diagnostics. Preserve full calculation precision and editable formulas. Display rounding must never alter stored monetary values. Formula examples and their explained source coefficients (such as the 2026 tax of 0.09161 EUR/kWh) retain the precision needed to reproduce the formula.
- Show every percentage with exactly one decimal place, including SoC, targets, error metrics, axes, tooltips, summaries and explanatory examples. Use the shared percentage formatter with the browser locale and preserve unknown values. Percentage inputs show one decimal while idle and their exact value while editing. Display rounding must never alter drafts, saved values, calculations or API precision. Keep formulas, identifiers and unit-only labels unchanged.
- Do not show redundant Home Assistant timezone or hover instructions as chart x-axis titles. Retain time ticks, date/time tooltips and explicit UTC calendar captions.
- Display UI dates and times with minute precision, without seconds. Use the shared `when` formatter for labels, tables, selectors, chart tooltips and diagnostic summaries. Keep original seconds and milliseconds in stored data, API contracts, calculations and date conversion logic.
- The Home Assistant installation is the only timezone authority. Do not expose an OEP timezone setting. Calendar rule dates start at 00:00 in that timezone. Actual deadlines retain a time picker. Use the installation timezone even when the browser runs elsewhere, and reject nonexistent DST wall times.

## Documentation

- Define fixed policy values, limits, thresholds, intervals and timeouts as meaningful named constants, including units where ambiguous. Keep each policy at its responsible module and import genuinely shared policy from one owner. Derive dependent horizons, time grids and step counts from the central planning policy. Do not duplicate 48/72/96/120 across consumers. Provider access limits remain separately named capabilities. Apply this style to existing production code when found, without changing values. Keep independent scenario inputs/expected results literal or separately specified. Never derive an oracle from the implementation constant. Arithmetic identities, tuple positions, protocol field names and descriptive example values do not require artificial constants. Tests must prove effective behaviour, not only compare a constant to itself.

- Ordinary live planning runs on UTC quarters. Meaningful input deviations/new source versions are coalesced behind the five-minute early-round limit. Do not turn measurement freshness deadlines or routine polling into solver triggers. Input admission age and published command lifetime are distinct policies.

- App diagnostics must use `logging.getLogger(__name__)` and the shared `runtime.diagnostics.logging` bootstrap. Every physical output line, including multiline messages and traceback/stack lines, uses the same UTC millisecond timestamp, level and logger format as lifecycle events. Do not add bare diagnostic prints or independent formatters/handlers. Ordinary updates must not starve publication: finish usable active calculations and coalesce updates for the next round. Only hard invalidation blocks publication, at INFO rather than ERROR. Actual unexpected failures retain their traceback. Never log credentials or tokens.

- Follow [the logging guideline](docs/development/LOGGING.md). Explain the operation, safe cause, effect on usable data/planning and actual next action or retry. INFO describes lifecycle and meaningful state changes or acknowledged results; DEBUG carries routine refreshes, repeated unchanged failures and technical identities; WARNING describes recoverable degradation; ERROR identifies unexpected failures with tracebacks. Deduplicate unchanged background failures and log recovery. Never promise an unimplemented retry or log success before acceptance/persistence. Keep provider payloads, credential-bearing URLs and precise locations out of diagnostics.

- HTTP errors must not expose arbitrary exception text. Admit only exact fixed domain-validation explanations at the responsible route, otherwise return owned recovery advice. Preserve unknown-failure type and stack locations without exception values, source lines or locals. Test both responses and server logs with private-value sentinels, including failures after durable writes and during response projection. Do not suppress findings merely because an exception is a `ValueError`.

- Well-documented code is required. Follow [the code documentation standard](docs/development/CODE-DOCUMENTATION.md): PEP 257 docstrings and Google-style extended sections, aligned with Home Assistant. Every authored production module, class, function and method needs a meaningful docstring. Explain non-obvious behaviour, contracts and decisions in proportion to complexity.
- Every test function needs a short docstring stating the situation and expected behaviour, not merely repeating its name. Planner scenarios must also explain why the expected outcome is correct, including independent arithmetic or a precise reference to its fixture's documented rationale. Document shared fixtures/helpers where their setup or assumptions matter. This applies to existing tests and all new/changed tests. Keep independent input values, assertions and expected numerical outcomes unchanged during documentation-only work.
- Document units, signs, efficiency/cost assumptions, validity, side effects, failure behaviour and concurrency/ownership where relevant. Comments explain why. Type hints express types. Update documentation with behaviour changes. The initial docstring-control adoption includes existing production code and scripts, without legacy exemptions.
- Documentation correctness and completeness are PR-review requirements. Do not substitute a percentage target, generated filler or a green lint result for review. Ruff enforces missing/empty public docstrings. Private/nested helper completeness and semantic quality remain review obligations. Keep CodeRabbit's percentage check disabled.

Keep `README.md`, `CONTRIBUTING.md`, `AGENTS.md` and legal notices at the repository root. Development guides belong in `docs/development/`. Requirements and architecture remain in `design/`. Update relative links and documentation checks after moves.

Maintain documentation only when it helps users or future maintenance. Describe the current behavior, supported configuration, contracts, limitations, relevant design rationale and reproducible validation commands. Update the canonical guide instead of appending implementation updates. Keep PR numbers, review conversations, temporary screenshots, dated run results and before/after delivery reports in the PR or CI artifacts, not in maintained product/site documentation. Git retains development history. Preserve legal notices, immutable provenance, independent test fixtures and actual application history. Those are not disposable delivery reports.
